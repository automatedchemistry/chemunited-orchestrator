# Software design

ChemUnited is split across independent packages that communicate over HTTP and plain files rather than importing
each other directly. This is what makes it possible for simulation and real-hardware execution to run **the exact
same protocol code** — one side just swaps in a different client underneath.

* **chemunited-orchestrator** — the PyQt5 desktop GUI. Authors the project's files (platform drawing, protocols,
  connectivity associations) and is the only piece most users ever open directly.
* **chemunited-core** — the shared data model for components and connections that both the workflow engine and
  simulation engine compile against.
* **chemunited-workflow** (the "work-server") — compiles a process into an executable graph and runs it against
  real hardware over HTTP, exposing a browser dashboard and REST/MCP API. See
  [The Dashboard](../dashboard/overview.md).
* **chemunited-sim** — the physics engine behind digital twins. Can either dry-run a protocol standalone, or
  mirror ("shadow") a live hardware run happening in chemunited-workflow. See
  [Setup Digital Twins](../simulation/digital_twins.md).
* **chemunited-quantities** — shared physical-unit types (`ChemUnitQuantity`) used by all of the above, so a
  volume or flow rate defined in the orchestrator means the same thing everywhere downstream.

## The Project Directory

Every ChemUnited project is a plain, git-versioned directory — there is no hidden database. A `.chemunited` file
is simply this directory zipped up for sharing or backup.

```text
my_project/
├── manifest.json                  # name, version, description, process order
├── draw/
│   └── setup.py                   # build_draw(platform) — the platform layout, generated by the Draw canvas
│                                   # (optionally build_graph_patch(graph) for manual topology fixups)
├── connectivity/
│   └── associations.json          # maps each canvas component to a live/simulated device URL
├── protocols/
│   ├── main_parameters.py         # global MainParameter model shared by all processes
│   ├── <process_name>.py          # one file per process: ProcessConfig + CustomProcess
│   └── __init__.py                # auto-generated PROCESSES/CONFIGS registry — do not edit by hand
├── protocols_historic/
│   └── <name>_<timestamp>.json    # saved protocol scripts (created via "Save Protocol Script")
└── pyproject.toml                 # makes the project directory pip-installable
```

## How Execution Happens

1. **Draw** — you lay out the platform; this is saved as `draw/setup.py`.
2. **Build Protocols** — you author one or more processes as workflow graphs; each becomes a `protocols/<name>.py` file.
3. **Pre-Running** — you choose which processes are active and in what order, forming the protocol to run.
4. **Run Monitoring** hands that protocol to the work-server (`chemunited-workflow`), which compiles it into a
   graph (nodes are process steps, edges carry conditions/loopbacks) and executes it with a thread-pooled
   scheduler, emitting live events to the [Monitor window](../monitoring/run_monitoring.md) and the
   browser dashboard's [Run Control](../dashboard/run_control.md) page.
5. **Run Simulation** instead hands the same protocol to `chemunited-sim`, which runs it against a physics model
   instead of real devices — see [Setup Digital Twins](../simulation/digital_twins.md).
